# Phase 3.1: Mob Spawn Runtime - Context

**Gathered:** 2026-03-25
**Status:** Ready for planning

<domain>
## Phase Boundary

Create the mob AND item spawn runtime — the systems that read definitions and create actual game objects. Mob spawner reads spawn_definitions from rooms, creates SoravelonMob instances with affixes and combat stats, attaches patrol scripts, manages respawn timers, and enforces count limits. Item spawner creates items from template definitions for loot drops, quest rewards, and tome drops. This bridges the gap between AreaBuilder's data definitions and living entities in the game world.

</domain>

<decisions>
## Implementation Decisions

### Spawn Timing
- **D-01:** Mobs spawn at zone load time (during `_load_all_zones()`). Zones are populated before any player enters.
- **D-02:** Spawning is STAGGERED to avoid DB write burst. Approach is Claude's discretion (callLater batches or TickerHandler spawn tick — planner decides based on Evennia architecture).
- **D-03:** On server reload, PRESERVE existing mobs. Only spawn mobs for rooms that are under count_min. Don't duplicate. Compare room contents against spawn_definitions.
- **D-04:** `no_mobs` room flag prevents mob entry entirely — no spawning AND no patrol routing through the room. This is a safe zone flag, not just spawn suppression.

### Respawn Mechanics
- **D-05:** Per-room respawn timer. When a mob dies, a lightweight timer fires after `respawn_minutes ± respawn_variance` (from spawn definition). Timer creates a new mob in that room.
- **D-06:** Respawn timers are NEVER hardcoded. Always from the spawn definition's `respawn_minutes` and `respawn_variance` fields (room-level or mob template-level).
- **D-07:** On server restart, all dead mobs respawn immediately. No need to persist timer state — restart = fresh respawn cycle.

### Spawn System Architecture
- **D-08:** New module: `world/mob_spawner.py`. Stateless functions: `spawn_room_mobs(room)`, `spawn_zone(zone_obj)`, `respawn_mob(room, spawn_def)`.
- **D-09:** Call chain: mob_spawner creates SoravelonMob → calls `apply_affixes_to_mob()` → calls `initialize_mob_combat_stats()`. Same chain as the existing `initialize_for_spawn()` on SoravelonMob.
- **D-10:** `spawn_zone(zone_obj)` iterates all rooms in the zone (by zone_id tag search), calls `spawn_room_mobs(room)` for each.
- **D-11:** `spawn_room_mobs(room)` reads `room.db.spawn_definitions`, for each definition: rolls count between count_min/count_max, creates that many mobs, initializes each.

### Named Mob Lifecycle
- **D-12:** Named mobs use custom respawn timer from `named_mob_definitions[].respawn_minutes`. No hardcoded values.
- **D-13:** Named mob dies → deleted → respawn timer fires → new instance created → zone announcement on respawn.
- **D-14:** Tome drops are PRE-ASSIGNED at spawn time. `tome_drop` from the definition stored on `mob.db.tome_drop`. If mob dies and has a tome_drop, the item is created (or stubbed until item spawn system exists).
- **D-15:** Named mobs registered in `named_mob_registry` at spawn time (already exists from AreaBuilder, but now the actual mob object is registered too).

### Patrol Integration
- **D-16:** If a spawn definition's `mob_template` matches a patrol definition (on zone_obj.db.patrol_definitions), the spawned mob gets a PatrolScript attached with the patrol route.
- **D-17:** Patrol routes skip rooms with `no_mobs` flag. `find_path()` should respect this.

### Count Management
- **D-18:** Each spawn definition tracks count_min/count_max. The spawner rolls a target count within that range on initial spawn.
- **D-19:** On reload/restart, count existing mobs matching the spawn definition in the room. Only spawn up to count_min if under.
- **D-20:** Respawn timer only fires if current count is below count_max for that definition.

### Action Vocabulary Integration
- **D-21:** Wire up the `spawn_mob` action type in `action_vocabulary.py` (currently stubbed). It should call `mob_spawner.spawn_single_mob()` to create a mob from a template.

### Item Spawn System
- **D-22:** New module `world/item_spawner.py` — creates item instances from template definitions. Stateless functions like mob_spawner.
- **D-23:** Item templates are data dicts (not DB objects). Stored as a registry in `world/item_templates.py` or loaded from JSON. Each template defines: key, item_type, weight, rarity, equip_slot (if equipment), description, and any special properties.
- **D-24:** `create_item_from_template(template_id, location=None)` creates a SoravelonItem/Equipment/Container from a template dict. Returns the created Evennia object.
- **D-25:** Wire `give_item` action to accept `template_id` (creates new item) in addition to `item_id` (existing dbref). If `template_id` present, call `create_item_from_template()` then `pick_up()`.
- **D-26:** Named mob `tome_drop` uses `create_item_from_template()` at mob death to produce the tome item.
- **D-27:** Item templates are the content-authoring surface — builders define items as templates, the spawn system instantiates them. This is the same pattern as mob spawn definitions.

### Loot Table System
- **D-28:** Extend `world/loot_tables.py` from stub to functional loot resolution. `roll_loot(mob, killer)` returns a list of item template IDs to drop based on mob rarity, loot tier modifiers, and skill-based material tiers.
- **D-29:** Loot tables are data-driven dicts keyed by mob_type or zone_id. Each entry defines: base_drops (guaranteed), bonus_drops (rolled per extra_roll from rarity), tome_chance, material_tier_override.
- **D-30:** `roll_loot()` is called from `SoravelonMob.at_death()` and creates items via `item_spawner.create_item_from_template()`. Items placed in the room (not directly in player inventory — group loot mode determines pickup).
- **D-31:** Material tier from loot is determined by the killer's relevant skill score (existing `get_material_tier()` in zone_scaling.py).
- **D-32:** Group loot mode (personal, ffa, round_robin, need_pass) determines who can pick up dropped items. For now, items drop to room — group loot enforcement is a Phase 6 concern. Phase 3.1 just creates the items.

### Patrol Integration in Spawner
- **D-33:** `_maybe_attach_patrol()` helper in mob_spawner.py. After creating a mob, checks zone_obj.db.patrol_definitions for a matching mob_template. If found, creates and attaches PatrolScript with the route.
- **D-34:** Patrol route room IDs (dbrefs) in the patrol definition are resolved to actual room objects via `evennia.search_object("#" + str(dbref))`.
- **D-35:** `find_path()` in patrol_engine.py must respect `no_mobs` room flag — skip rooms with tag `no_mobs` in category `room_flag` during BFS traversal.

### Claude's Discretion
- Stagger approach (callLater vs TickerHandler — whatever works cleanest with Evennia)
- Mob template lookup mechanism (how spawn_definitions reference mob types)
- Respawn timer implementation (Twisted callLater, Script, or TickerHandler)
- Named mob zone announcement format
- Item template storage format (Python dict registry vs JSON file)
- Whether item templates live in area spec files or a separate item data file
- Loot table data structure details (exact dict format, fallback chains)
- Whether loot drops are visible to all players in room or just the killer's group

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `initialize_for_spawn(room)` on SoravelonMob already calls apply_affixes + initialize_combat_stats. mob_spawner should use this or replicate the chain.
- `evennia.search_tag(zone_id, category="zone_id")` finds all rooms in a zone — used for spawn_zone iteration.
- `named_mob_registry.register_named_mob()` already exists — call it when named mobs are actually spawned.
- `typeclasses/objects.py` has SoravelonItem, SoravelonEquipment, SoravelonContainer, SoravelonKeyringItem — item_spawner creates instances of these.
- `world/inventory_engine.py:pick_up()` handles InventoryItem record creation — used after item creation.

### Integration Points
- `_load_all_zones()` needs to call `spawn_zone()` after each zone's build() completes
- `SoravelonMob.at_death()` needs to schedule respawn timer + create tome drop item
- `action_vocabulary._action_spawn_mob` needs to be unwired from stub
- `action_vocabulary._handle_give_item` needs template_id support (create new item, not just dbref lookup)
- `find_path()` needs to respect room `no_mobs` flag

</code_context>

<specifics>
## Specific Ideas

- The `no_mobs` flag should be a room tag (category="room_flag") or a db attribute. Tags are indexed and faster to query.
- Named mob zone announcements should use the echo action vocabulary: `{"type": "echo", "text": "...", "target": "zone"}`.
- Respawn timers should be Twisted `callLater` (one-shot, non-persistent). On server restart, the staggered spawn pass handles refilling dead mobs.

</specifics>

<deferred>
## Deferred Ideas

- Mob template registry (formal template system vs. hardcoded mob_type strings) — future work
- Dynamic spawn adjustments based on player count in zone — future
- Pack spawning from spawn definitions (mob_affix_roller already has pack spawn, but integrating it with room definitions is additional scope)
- NPC spawning (npc_definitions are stored but not spawned — separate from mobs)

</deferred>
